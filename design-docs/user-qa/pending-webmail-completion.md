## 1. Multi-recipient inbound storage (default: D8)

When one inbound message reaches several managed mailboxes, the default
stores **one row per recipient domain, with one ENVELOPE recipient row per
delivered mailbox on that domain**.

Mailboxes on the same domain (for example `a@tacoserve.online` and
`b@tacoserve.online`):
- The mail is one row and appears once in "All mail", once in the domain
  scope, and in each mailbox scope.
- Read state, tags, spam verdict and Trash are shared between those
  mailboxes.

Mailboxes on different domains (for example `alice@tacoserve.online` and
`bob@mutvar-test.online`):
- The mail is two rows that share one thread.
- Each row appears in its own domain scope and mailbox scope, and is
  readable by anyone authorized on that domain and address.
- "All mail" lists both rows.
- Each row has its own read state, tags, spam verdict and Trash state.

This is required because a message row has a single `domain_id`, and both
the domain filter and the permission rules key on it.

Alternatives:
- One independent copy per individual mailbox, even within a domain. This
  needs a mailbox column and shows duplicates for same-domain recipients.
- One row across domains. This needs new multi-domain filter and
  authorization predicates.

Confirm the default, or ask for an alternative.

## 2. Live checks owned by the orchestrating session (no user decision)

None of these can be verified without deploying. They need a live check
after deployment:

1. **Threading headers.** Does the deployed `send_email` binding accept
   `Message-ID`, `In-Reply-To` and `References` in `headers`?
   - If it rejects them, sends fail as `MESSAGE_REJECTED`.
   - The contingency is the raw `EmailMessage` form: one call per envelope
     recipient, with a Bcc-free MIME source.
2. **Provider message id.** What does `EmailSendResult.messageId` contain?
   The design persists it as `rfc_message_id` when it differs from ours, so
   that external replies still thread.
3. **Cross-domain delivery.** A send from `tacoserve.online` to
   `mutvar-test.online` (and back) should appear in the Sent folder of the
   sending mailbox and the Inbox of the receiving one.

### Live check results (deployed binding, measured with a throwaway Worker)

All of these were sent through `env.EMAIL.send(builder)` from
`taco@tacoserve.online`, with `to: ["taco@mutvar-test.online"]` and
`cc: ["info@mutvar-test.online"]`. The domains are onboarded to Cloudflare
Email Sending, and neither recipient is a verified Email Routing destination.

1. **Threading headers.**
   - `headers: { "In-Reply-To": "<x>", "References": "<x>" }` is accepted.
     The inbound copy has `inReplyTo` and `references` set correctly.
   - `headers: { "Message-ID": "<...>" }` is **rejected**, with
     `E_VALIDATION_ERROR`: "custom header 'Message-ID' is not allowed. Only
     whitelisted headers and X-* headers are accepted."
   - Never pass Message-ID. Persist the provider id instead.
2. **Provider message id.** The send result is
   `{ messageId: "<AE8o...@tacoserve.online>" }`.
   - It is angle-bracketed and generated by the provider on the sender's
     domain.
   - Inbound, the recipient sees that exact value as its Message-ID (stored
     without brackets).
   - So the outbound row's `rfc_message_id` must be updated to the provider
     value, without brackets, or external replies will not thread.
3. **Cross-domain and multi-recipient delivery.**
   - A single builder call with `to` and `cc` arrays delivered to both
     mailboxes.
   - The inbound copy carries correct `TO` and `CC` header recipients.
   - The current per-recipient fan-out in `cloudflare-email.ts` is wrong:
     it rewrites To per recipient, drops Cc, and drops attachments. Replace
     it with one builder call that uses arrays.
4. **Other fields.**
   - `replyTo: "addr"` is accepted.
   - `from: { email, name }` (display name) is accepted.
5. **Attachments.** These are accepted:
   - `attachments: [{ content: <base64 string>, filename, type,
     disposition: "attachment" }]`
   - An inline item with `disposition: "inline"` and `contentId: "logo1"`.

   Inbound, both arrive. However, the **inline** part's `fileName` is stored
   as the generic `"attachment"`. Ingest should fall back to the
   Content-Type `name=` parameter, or to `inline-<cid>.<ext>`, and should
   mark it as inline with its content id so `cid:` rewriting works.
